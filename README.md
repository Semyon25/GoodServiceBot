# GoodServiceBot — вынос мусора в ЖК «Заречье Парк»

Telegram-бот для покупки подписки на вынос бытового мусора и оформления заявок
на вынос пакета от двери квартиры. Роли: клиент, исполнитель, администратор.

Стек: Python 3.11+, aiogram 3.x, SQLite (aiosqlite).

## Установка

Нужен **Python 3.11 или новее** (проверено на 3.13). Папку `.venv` нельзя копировать
с другого компьютера — создавайте её заново на каждой машине.

Windows (через лаунчер `py`, чтобы точно взять нужную версию):

```bash
py -3.13 -m venv .venv
```

Linux:

```bash
python3.13 -m venv .venv
```

Установка зависимостей, Windows:

```bash
.venv\Scripts\pip install -r requirements.txt
```

Linux:

```bash
.venv/bin/pip install -r requirements.txt
```

## Настройка

Скопируйте `.env.example` в `.env` и заполните:

| Переменная | Обязательна | Описание |
|---|---|---|
| `BOT_TOKEN` | да | Токен бота от @BotFather |
| `ADMIN_IDS` | да | Telegram ID администраторов через запятую |
| `DB_PATH` | нет | Путь к файлу SQLite, по умолчанию `data/bot.sqlite3` |
| `TIMEZONE` | нет | Часовой пояс расписания, по умолчанию `Europe/Moscow` |
| `LOG_LEVEL` | нет | `DEBUG` / `INFO` / `WARNING` / `ERROR` |
| `JOBS_INTERVAL_SECONDS` | нет | Период фоновых проверок (напоминания о подписке, заявки без исполнителя), по умолчанию 60 |
| `PROXY_URL` | нет | Прокси до api.telegram.org: `http://host:port`, `socks5://user:password@host:1080` |

### Нет связи с Telegram

Боту нужен исходящий доступ к `api.telegram.org:443`. Если его нет (корпоративная сеть, блокировка
провайдера), в логе будет «Нет связи с api.telegram.org … Превышен таймаут семафора» — бот не падает,
а повторяет попытку каждые 15 секунд. Варианты:

* запустить бота на сервере или в сети, откуда Telegram доступен (проверка — открыть
  `https://api.telegram.org` в браузере на этой машине: должна открыться страница, а не ошибка соединения);
* указать прокси в `PROXY_URL`;
* включить VPN на компьютере, где запущен бот.

Если токен неверный, бот сразу завершится с сообщением «Telegram отклонил BOT_TOKEN».

Свой Telegram ID можно узнать, например, у бота @userinfobot.
Файл `.env` содержит секреты — не публикуйте его и не добавляйте в систему контроля версий.

Реквизиты СБП, тарифы, расписание, адреса и тексты **не** задаются в `.env` —
их меняет администратор прямо в боте (см. [docs/ADMIN.md](docs/ADMIN.md)).

## Запуск

```bash
python -m bot
```

(запускать из корня проекта, интерпретатором из `.venv`).

При первом запуске создаётся файл базы и заполняются начальные данные:
3 адреса, услуга «Вынос мусора», тарифы «Неделя» 200 ₽ / 7 дней и «Месяц» 600 ₽ / 30 дней,
расписание Пн–Пт 19:00–01:00 (приём), выполнение до 02:00.

### Запуск на сервере (systemd)

```ini
# /etc/systemd/system/goodservicebot.service
[Unit]
Description=GoodServiceBot
After=network-online.target

[Service]
WorkingDirectory=/opt/goodservicebot
ExecStart=/opt/goodservicebot/.venv/bin/python -m bot
Restart=always
RestartSec=5
User=goodservicebot

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable --now goodservicebot
```

Резервная копия — это копия файла базы (`data/bot.sqlite3`, а также `-wal`/`-shm` рядом с ним,
если бот запущен). Надёжнее всего копировать при остановленном боте или командой
`sqlite3 data/bot.sqlite3 ".backup backup.sqlite3"`.

## Обновление и миграции БД

Версия схемы хранится в `PRAGMA user_version`. При каждом запуске бот применяет недостающие
миграции из `bot/db/migrations.py` (каждую — в отдельной транзакции), существующие данные
сохраняются. Чтобы изменить схему, добавьте в список `MIGRATIONS` новую запись со следующим
номером; уже выпущенные миграции не редактируются.


Покрыты: расписание смен, оплата и подписки, ограничения заявок, статусы заказа,

## Структура

```
bot/
  __main__.py          точка входа
  config.py            загрузка .env
  jobs.py              фоновые задачи (напоминания, неназначенные заявки)
  domain/              модели, статусы, допустимые переходы, расчёт смен — без зависимостей от БД и Telegram
  db/                  подключение к SQLite, миграции, репозитории (весь SQL здесь)
  services/            бизнес-логика: пользователи и адреса, тарифы, платежи и подписки, заказы, отчёты
  telegram/            тексты, клавиатуры, middleware, уведомления и обработчики (client, executor, admin_*)
tests/
docs/
  ADMIN.md             инструкция администратора
  SBP.md               инструкция по изменению реквизитов СБП
```

## Ключевые решения

* **Роли.** Администраторы задаются только в `ADMIN_IDS`. Роль исполнителя назначает администратор.
  Права проверяются в сервисах при каждом действии, а не только скрытием кнопок.
* **Смены.** Смена с датой D: приём заявок D 19:00 — D+1 01:00, выполнение до D+1 02:00.
  00:00–02:00 относится к смене предыдущего рабочего дня. Все времена — Europe/Moscow,
  в БД хранятся в UTC.
* **Одна заявка в смену.** Уникальный индекс `(клиент, услуга, дата смены, номер попытки)`.
  Повторные и одновременные нажатия не создают дублей. Администратор может разрешить
  исключение — тогда допускается ещё одна попытка.
* **Оплата.** Только ручной перевод через СБП. «Я оплатил» + чек переводит платёж в
  «Ожидает подтверждения»; подписка создаётся только при подтверждении администратором.
  У подписки уникальная ссылка на платёж, а триггер БД проверяет, что платёж подтверждён и
  суммы совпадают — повторное подтверждение не создаёт вторую подписку.
* **Подписки.** Сумма и срок фиксируются в платеже в момент выбора тарифа, поэтому изменение
  тарифа не влияет на оплаченные периоды. Новая подписка начинается после окончания текущей.
  Возврат денег аннулирует связанную подписку.
* **Статусы.** Таблицы допустимых переходов заказов и платежей хранятся в БД и проверяются
  триггерами; история переходов пишется в `order_status_history` / `payment_status_history`,
  административные действия — в `admin_actions`.
* **Адрес в заказе.** Заказ хранит копию адреса на момент создания, а адрес клиента
  версионируется — изменение адреса не меняет уже созданные заказы.
* **Новые услуги.** Услуга (`services`) хранит код, название, описание, активность,
  собственное расписание (`schedule_json`, иначе общее) и правила (`rules_json`,
  например `max_orders_per_shift`). Тарифы, подписки, платежи и заказы ссылаются на услугу.
  Экраны для будущих услуг в первую версию не входят.
* **Распределение заявок.** Режим переключается в «⚙️ Настройки»: «Назначает администратор»
  (по умолчанию) или «Общий пул» (новые заявки видят все исполнители, первый принявший забирает).

## Ограничения первой версии

* Состояние незавершённых диалогов (например, ввод адреса) хранится в памяти и сбрасывается
  при перезапуске бота — пользователю нужно просто начать действие заново. Данные в БД не теряются.
* Праздничные дни не учитываются — рабочие дни задаются днями недели.
